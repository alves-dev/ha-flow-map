# Context Mesh Framework

## Overview

Context Mesh keeps durable project knowledge close to the code it describes. Work follows three connected steps:

1. **Intent** — record what is being delivered and why it matters.
2. **Build** — make an approved change while following recorded decisions and patterns.
3. **Learn** — record outcomes, discoveries, and changes to the project context.

## File-Type Separation

- `intent/feature-*.md` records **what** a capability does and **why** users need it. It may contain functional acceptance criteria, but never implementation details, library names, code paths, or code examples.
- `decisions/*.md` records technical **choices**: architecture, frameworks, APIs, constraints, rationale, and alternatives.
- `knowledge/patterns/*.md` records reusable **how-to-implement** conventions with code examples and file locations.
- `knowledge/anti-patterns/*.md` records practices to avoid and their safer alternatives.
- `agents/*.md` contains narrowly scoped instructions for agents when such instructions are needed.
- `evolution/` records changes, outcomes, and learning over time.

Features should link to the applicable decisions and patterns. Decisions and patterns should link back to the affected features. Do not duplicate a technical explanation in a feature merely to make it self-contained.

## Mandatory Plan, Approve, Execute

For a new or material change, follow this sequence:

1. **Plan** — load project intent plus the relevant feature, decision, and pattern files; identify the intended behavior and proposed technical approach.
2. **Approve** — obtain the required approval before implementing a material or externally visible change. Existing, already implemented behavior is documented as accepted historical context.
3. **Execute** — implement the approved change, validate it, and update intent, decisions, patterns, and evolution records as needed.

Do not silently turn an implementation detail into a feature requirement, or invent a technical decision without recording the uncertainty.

## When to Create or Update Files

Create or update an intent file when behavior, users, value, or acceptance criteria change. Create a decision when a durable technical choice is made or materially changed. Create a pattern when a reusable implementation convention with an example emerges. Update an existing record instead of creating a duplicate when it describes the same concern. Do not create files for incidental formatting, one-off investigation notes, or transient debugging unless the learning will guide future work.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/
├── decisions/
├── knowledge/
│   ├── patterns/
│   └── anti-patterns/
├── agents/
└── evolution/
```

## Bidirectional Links

Use relative Markdown links. Every feature links to its applicable decisions and, where useful, patterns. Each linked decision or pattern links back to the feature. Decisions link to related decisions where one constrains another. Prefer links over copied explanations; verify paths whenever files are renamed.

## Status Requirements

Every intent, decision, pattern, and evolution record includes a `Status` section. It states creation date, lifecycle status, and a short note when helpful. Existing-code documentation must make clear when rationale or alternatives are inferred rather than recorded by the original authors.

## Definition of Done

A build-phase change is complete only when the relevant intent is accurate, a decision exists before implementing a material technical choice, the implementation follows the documented patterns, applicable validation passes, reciprocal links are correct, and `evolution/changelog.md` reflects the change. Significant results or deviations are recorded as decision outcomes or learning.
